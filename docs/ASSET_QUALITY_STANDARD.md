# PINE アセット品質基準・制作ルール（必須）

更新日: 2026-11-17

## 目的
PINEでは、配置する**すべてのブロック、床・地形タイル、壁・窓・扉・屋根、橋・港、家具、乗り物、自然物、設備、装飾、NPCに関わる外見**について、可能な限り高い品質と説得力を追求する。単に立方体を組んで機能を満たすだけでは不十分。プレイヤーが発見して近づき、使い、歩き回りたいと思う景観を目指す。

ただし、Android WebView・オフライン単一HTML・容量上限12MB・描画性能・タイル単位の操作性と両立させる。高品質は「高ポリゴン化」だけではなく、形状・配置・色・素材の特徴・全体の統一感・適切なディテールで実現する。

## 新しいアセットを作る前の必須調査
1. **用途と実在の構造を特定する。** 例：桟橋なら杭・桁・床板・護岸・係船柱・防舷材・手すり・船との高低差。住宅なら基礎・外壁・屋根勾配・玄関・排水・階段・間取り。
2. **写真や資料で実物を確認する。** 可能なら正面・側面・上方・近景を参照し、部品のつながり、寸法比、素材、施工の合理性を読み取る。構造的に重要な対象は複数の信頼できる資料で照合する。
3. **評価の高いゲームの画面・公式画像も比較する。** どの特徴が少ないポリゴンでも認識しやすいか、色分け、シルエット、劣化・汚れ、生活感をどう表現しているかを研究する。写真とゲーム画像の役割を区別する。
4. **PINE向けの設計メモを残す。** 調べた特徴、採用する構造、簡略化する箇所、使用ブロック、想定寸法、屋内外の接続、歩行できる面、他のアセットとの調和を明記する。
5. **調査できなかった場合は正直に記録する。** 画像や資料を確認していないのに「参考画像を検証済み」とは書かない。ネット検索ができない環境では、既に記録された資料・既存の観察結果だけを根拠に、暫定案と明記する。

## モデルと景観の評価軸
- **シルエット:** 遠くから見ても用途・種類・年代の違いが分かるか。
- **構造:** 実際の重力・荷重・接続・開口・排水・通行の理屈に反しないか。
- **スケール:** 人・道路幅・ドア・船・岸壁・家具との比率が自然か。
- **ディテール:** 主要部材、窓枠、屋根端、柱、手すり、継ぎ目、固定具などを用途に応じて選ぶ。無意味な飾りを増やさない。
- **素材と色:** 木、石、鉄、コンクリート、布、ガラスなどの違いを形と色で認識できるか。単調な色・過剰な彩度を避ける。
- **経年変化:** ゾンビ災害後の世界観に適したサビ、退色、欠損、植物の侵入、応急修理、生活の痕跡を状況に合わせる。
- **配置と文脈:** 何のためにそこに建てられたか、隣接する道路・施設・地形と連続するか。歴史ある住民区と仮設の避難民キャンプ、軍の施設の設計差を表す。
- **使用可能性:** 扉は入れる、階段は登れる、橋は渡れる、船は接岸できる。景観と衝突・歩行判定が一致する。
- **視認性:** 真上寄り3D視点・モバイルの小さい画面でも重要な形が読めるか。手前の屋根やオブジェクトが探索の邪魔をしないか。
- **性能:** 近景では必要なディテールを維持し、遠景ではメッシュや装飾の数を抑える。毎フレームの再生成を避ける。

## 制作・実装の順序
**調査 → 観察メモ → 形状設計 → ワールドエディターで試作 → 現物/参考との比較 → 共通建材として実装 → ゲームで配置・歩行・描画確認 → 軽量化 → 記録**。

既存アセットを改善する場合も、元の用途・姿・景観との関係を観察してから行う。既存の農地・橋・住居・道路を消して新モデルを無理に配置しない。テストマップ上で改良案を作り、完成を確認するまで本編の旧アセットは温存する。

## 参考資料の扱い
- 調査した実写写真、設計図、公式ゲーム画像、現地映像などの**出典URL・題名・確認日・学んだポイント**を `docs/ASSET_REFERENCE_LOG.md` に記録する。
- ゲーム画像からは「なぜ見やすく美しく感じるか」を学び、既存ゲーム固有のモデル・テクスチャ・画像を無断で複製しない。著作物の直接トレース・無断再配布は避け、PINE独自のアセットを制作する。
- 参考画像をゲームHTMLに無断で取り込まない。必要な素材は権利やライセンスを確認する。
- 画像を確認したこと、確認できなかったこと、仮説と事実を区別する。

## 必須の完成判定
1. エディターとゲーム本体で同じブロックID・外見・向き・床/障害物の意味になる。
2. 参考資料に基づく構造的特徴が反映され、近景・遠景の両方で不自然な形状がない。
3. 主要な接続部分（橋端・港の岸と桟橋・ドア・階段・車両の接岸）が途切れず、歩行と高さに矛盾がない。
4. 既存建物・畑・道路などに衝突・重複せず、世界観や周囲の景観に自然になじむ。
5. 端末負荷と単一HTML容量を確認し、著しく重くなる変更は採用しない。
6. 仕様・調査ログ・変更履歴を更新する。実機テストをしていない場合は未検証と記す。

**品質に疑問がある状態で「完成」と扱わない。** 形だけの橋・道路・港・建物を、見た目だけの仮実装で済ませない。
